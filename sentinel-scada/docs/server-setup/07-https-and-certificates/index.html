Part 7: HTTPS and Certificates

Goal Encrypt the connection between the server and its browsers, so that passwords and live data cannot be read by anyone else on the network, and make every client trust the server’s certificate.
Draft Outline only. Text and screenshots to follow.

This part assumes the server from Part 3 is working. It applies equally in XML mode and, after Part 6, in SQLite mode.

Why bother, on a private network?

What HTTPS protects against, in plain terms, and what it does not: it encrypts the traffic, but you still need authentication on and the default passwords changed.

Names, not addresses

A certificate is issued for a name, and browsers check it against the address you type. Clients must browse by the server’s host name, not its IP address.

Making a certificate

Using Generate New in the Launcher, or the New-SentinelCert.ps1 script, and choosing the names to include. Keep localhost in the list.

Switching HTTPS on

The Launcher’s Advanced Settings: Enable HTTPS, the port (5443 by default), the certificate file and its password. Opening the firewall for the HTTPS port.

Trusting the certificate

On the server: Trust Certificate Locally, and why the browser must be fully closed and reopened afterwards. On every other computer: exporting the public certificate with Export Public Cert, importing it, and where a hosts-file entry is needed for the name.

Checking it works

The padlock, the certificate details, and a live screen that updates.

What changes once HTTPS is on

  • The plain HTTP port redirects network browsers to HTTPS. At the server itself, http://localhost:5000 still works.
  • Browsers are told to keep using HTTPS for the next seven days.
  • Session cookies are marked secure.
  • Every restart of the server returns it to Design Mode, and a remote client waits until the console selects Run.

Troubleshooting

Certificate warnings, a name that does not match, a browser that still shows the old state, and the remembered-upgrade problem when turning HTTPS off again.
